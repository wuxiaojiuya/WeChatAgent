# 微信引用消息解析

接入 Hook 回调接收服务 → Hook OneBot → Social Bridge → DSH 的消息链。附件理解的模型与权限边界见 [媒体理解](MEDIA_UNDERSTANDING.md)。

## 接收与身份

支持类型 `49` 与 `(57 << 32) | 49`，同时要求 Hook 回调 XML 的 `appmsg/type=57`。直接解析回调提供的原始内容，不查询数据库或补查微信历史。其他 appmsg 类型不因此作为普通文字放行。

当前回复来自 `appmsg/title`；引用历史来自 `refermsg`。保留原消息的服务器 ID（字符串，避免大整数精度损失）、发送者、显示名、时间、类型和正文。群聊 `fromusr` 是群号，引用发言人是 `chatusr`；私聊发言人来自 `fromusr`。本地白名单里的真实私聊和群聊记录已用于核对这一差异。

当前消息的发送者取 Hook 回调中经归一化的发送者，不被 XML 中的引用者替代。接收服务根据项目连接及原群号计算引用来源关系，覆盖载荷中的关系标记；无法确认来源或来自另一群时标记未知。身份匹配只用于接话判断，不授予配置、工具或发送权限，也不证明那段话一定由当前人格发出。

## 模型上下文

`quoteReply` 作为有界结构经过 OneBot 归一化和聊天缓冲持久化。只保存一条当前发言，提示词中分别标注“被引用的历史消息”和“当前发言人的新回复”。引文中的标签会转义，规则变更指令作为历史聊天数据处理。

在群聊 `mention` 模式下，引用本账号的发言可触发决策，模型仍结合正文、相邻发言与上下文判断回应或沉默。引用其他人不自动触发；回复正文中的真实 @ 或唤醒词仍按既有规则处理。`hybrid` 模式继续通过普通消息批次判断。私聊继续按私聊规则处理。

## 边界

XML 上限 100,000 字符，回复保存至多 4,000 字符，引用原文至多 1,600 字符，嵌套引用最多展开 2 层；过长内容标注截断，模型批次仍遵守现有长度限制。DTD、ENTITY、无效 XML 和其他 subtype 被拒绝。

缺少引用原文时仍传递新回复，并说明原文不可用。引用附件通过完整服务器消息 ID、聊天、原发送者和类型匹配项目缓存的原消息；只有匹配成功才登记绑定的附件引用。图片/表情走视觉输入；语音走已授权的识别插件；视频提供采样画面和音轨；文本、PDF、DOCX 文件提取有界正文。原消息、媒体下载信息或授权不足时保留真实占位，不根据文件标题猜内容。不把媒体 XML、下载凭据或本机路径作为聊天文字。

读取结果标记为历史附件资料，当前回复与发言人不被原消息替换。引用文件的只读权限独立于通用文件工具，不因此授予助手下载其他文件或执行附件的权限。嵌套 appmsg 引用仍仅提供安全文字摘要。

接收支持解析别人发送的引用回复；当前 supplier-http 发送端另支持原生引用回复。同会话原消息必须已保存在项目缓存，由缓存提供原文、发送者、完整服务器 ID 与时间；缺失时明确失败，不查询微信数据库或猜测引用信息。

## 验证

Python 覆盖两种类型、群与私聊身份、回调 XML、大整数 ID、项目缓存引用、媒体占位、缺失内容、嵌套、恶意 XML 和截断。JS 覆盖 Hook → OneBot → 持久化恢复 → 模型提示词、来源关系覆盖、引用他人不误唤醒，以及伴随真实 @ 的接话。

当前 Hook 接收与引用回归使用模拟回调和项目缓存，不读取微信数据库。本次迁移未向联系人发送测试消息。

此前曾现场复核 8 条真实引用（5 条群聊、3 条私聊）及独立 DSH 原生会话；这些历史记录不能代替本次 Hook 接入的真实端到端验收。私有统计保存在 `state/diagnostics/quote-records-live.json` 与 `quote-model-live.json`，不属于公开源码。
